## A. Что исправлено

### P0 — Безопасность

1. **Открытые API-маршруты** → глобальный guard `auth/guard.ts` (onRequest-хук):
   всё под `/api` требует сессии владельца, кроме явного allowlist. Проверка
   на сервере ДО хендлера, для всех методов (GET/POST/PATCH/PUT/DELETE) —
   защита «только на frontend» больше не существует.
2. **`/api/telegram/setup-webhook` принимал URL из тела** → маршрут:
   - закрыт авторизацией владельца;
   - тело запроса игнорируется (схема-«пустой контракт»), URL строится
     ТОЛЬКО из серверной конфигурации (`TELEGRAM_WEBHOOK_URL` /
     `RENDER_EXTERNAL_URL`) — перенаправить апдейты бота на произвольный
     URL нельзя;
   - установка без секрета webhook запрещена.
3. **Webhook fail-open при пустом секрете** → `routes/telegramWebhook.ts`:
   пустой секрет в конфигурации → приём выключен (403, лог предупреждения);
   сравнение секрета `X-Telegram-Bot-Api-Secret-Token` — timing-safe
   (`timingSafeEqual`), неверный/отсутствующий → 401.
4. **CORS `origin: true` (любой источник)** → `auth/cors.ts`: только
   доверенные origin из `TRUSTED_ORIGINS` (прод-домен + localhost для
   разработки), credentials только для них; мутирующие запросы с
   посторонним Origin → 403 `FORBIDDEN_ORIGIN` (CSRF-глубина поверх
   SameSite=Lax). Попутно исправлен технический дефект: boolean-возврат из
   origin-функции @fastify/cors вешал запрос (обязательна callback-форма).
5. **Открытые маршруты парсера** → `/api/parser/run|status` закрыты
   авторизацией; Node → Python ходит с внутренним секретом `PARSER_SECRET`
   (заголовок `X-Parser-Secret`, только сервер-сервер); в production без
   `PARSER_URL` — честный 503 `PARSER_NOT_CONFIGURED`, а не молчаливый
   localhost:8000.
6. **Публикация `confirm: true`** — осталась, но теперь требует
   авторизации владельца: обход анти-бана без аутентификации невозможен.
7. **`/api/user/profile` (ИНН, ОГРНИП, банк)** — за авторизацией (guard);
   DTO не отдаёт ничего лишнего, ошибки не раскрывают SQL/пути
   (существующий `errors.ts` маппит Prisma-ошибки в коды).

### P0 — Аналитика

8. **Ложная атрибуция лидов** («последняя публикация позиции = источник
   лида») → настоящая атрибуция: deep link объявления `lst_{listingId}`
   в `telegram/publish.ts`, касание записывается в `LeadTouch`,
   `Lead.firstListingId/firstChannelId` (First Touch, не перезаписывается)
   и `lastListingId/lastChannelId` (Last Touch, обновляется). Старые
   ссылки `pos_…` продолжают работать, но канал НЕ приписывается
   (не выдумываем). Лид без достоверного источника в каналы не попадает.
9. **Конверсия > 100%** → считаем по УНИКАЛЬНЫМ лидам: лид с 2 сделками =
   1 сконвертированный; конверсия математически ≤ 100%.
10. **Выручка по `createdAt`** → отбор по `closedAt` (дата закрытия):
    сделка, созданная в прошлом периоде и закрытая сегодня, попадает в
    выручку сегодня. Старые закрытые сделки без даты (legacy) не
    выдумываются — учитываются только в «всё время».
11. **Тихие лимиты выборки (500/500/1000/200)** → агрегаты считаются в
    PostgreSQL (`$queryRaw` SUM/COUNT/FILTER/groupBy): итоги всегда по
    полному набору данных, лимитов нет вообще.
12. **`averageReach ?? subscribersCount` подменяло охват** → поля
    разделены: `subscribersCount` и `averageReach` независимо; UI и CSV
    показывают «подписчики X · ср. охват Y/неизвестен».
13. **`daysInStock` от `createdAt`** → от `stockSince` (фактическое начало
    наличия): проставляется при создании позиции в IN_STOCK и при возврате
    в IN_STOCK; для старых позиций null = «неизвестно».
14. **Часовой пояс сервера для дневных границ** → `shared/time.ts`
    (Europe/Moscow, фикс. UTC+3): `dayStartMoscow`, `weekStartMoscow`,
    `monthStartMoscow`, границы периодов; «новых лидов сегодня» считается
    по московскому дню.
15. **Средняя цена продажи как среднее цен** → средневзвешенная:
    `Σ(salePrice×volume) / Σ volume` (выручка / проданный объём).

## D. Аналитика — как считаем теперь

| Показатель | Логика |
|---|---|
| Атрибуция лида каналу | **Last Touch** по умолчанию: канал последнего достоверного перехода по deep link объявления (`lst_…`). First Touch сохраняется отдельно (`firstChannelId`). История касаний — `LeadTouch` (дедуп по [leadId, listingId]). Лиды без достоверного источника (включая старые `pos_`-ссылки) каналу не приписываются |
| Конверсия | уникальные лиды: `N_уникальных_лидов_со_сделками / N_уникальных_лидов × 100%`; лид с несколькими сделками = 1 сконвертированный; конверсия ≤ 100% |
| Выручка/маржа/закрытые | по `closedAt` за период («всё время» — все CLOSED, включая legacy без даты) |
| Итоги | SQL-агрегаты по полному набору (`SUM`, `COUNT … FILTER`, `GROUP BY`, `groupBy` Prisma) — без лимитов выборки |
| Охват | `subscribersCount` и `averageReach` — раздельные показатели; null = «неизвестно», подстановки нет |
| Дни в наличии | от `stockSince` (текущий непрерывный период наличия); null → «неизвестно» |
| Средняя цена продажи | средневзвешенная: `выручка / проданный объём` |
| Дневные границы | Europe/Moscow (shared/time), «новых сегодня» — по московской полуночи |
| Периоды | «неделя»/«месяц» — катящиеся окна 7/31 дней (семантика UI сохранена) |

## E. Парсер — источники и ограничения

- **Разрешено и работает по умолчанию**: Агросервер — только
  sitemap-путь; robots.txt обязателен (недоступен → отказ, TTL 1 ч),
  лимит 1 запрос / 2 сек, `/search/` не используется.
- **Выключено по умолчанию**: MTProto-сбор публичных Telegram-каналов
  (`TG_COLLECT_ENABLED=0`) — собирать чужой контент без подтверждённого
  права нельзя; включается вручную для источников, где право есть
  (свои каналы, официальные API).
- **Сниппеты**: ≤120 символов, вычищаются телефоны/@usernames/e-mail/URL;
  полная анонимизация не гарантируется и не заявляется.
- **Запуск**: `/run` только с внутренним секретом `PARSER_SECRET`
  (сервер-сервер); публичный запуск невозможен; конкурентные вызовы
  не запускают второй обход.
- **Деплой-схема**: в `render.yaml` задокументированы `PARSER_URL` +
  `PARSER_SECRET` для agropost-api и готовый (закомментированный) блок
  сервиса `agropost-parser`. Без них API и UI честно показывают
  «Парсер не настроен» (чек-лист readiness + карточка позиции).

## I. Оставшиеся проблемы / ограничения

1. **Деплой на прод не выполнялся** (по условиям этапа) — изменения
   попадут в прод только после мержа ветки и деплоя Render. Перед мержем
   задать в env agropost-api: `OWNER_LOGIN`, `OWNER_PASSWORD_HASH`
   (`cd apps/server && bun run hash-password`), `TRUSTED_ORIGINS`,
   при желании `PARSER_URL` + `PARSER_SECRET`.
2. **Логи Fastify** на 501/500 печатают стек ошибок — внутренние данные
   не раскрываются клиентам (единый формат `{error:{code,message}}`),
   но стеки видны в логах Render. Допустимо; при желании — уровень
   логов можно занизить.
3. **Интеграционные тесты парсера с БД** (`test_db_insert`) требуют
   доступной СУБД: в песочнице глобальный `DATABASE_URL` указывает на
   недоступный хост, поэтому офлайн-прогон показывает 39/41 (2 пропущены
   сетью, не кодом). С тестовой базой Neon — 41/41.
4. **Golden-сет AI** прогоняется на фикстурах (без живых ключей) —
   как и на этапе 5; живые вызовы не проверялись.
5. **Сессии в БД**: Render free tier спит — при пробуждении сессии живы
   (в БД), истёкшие вычищаются лениво при следующем входе.
6. **Аналитика каналов** считает «сделки канала» по лидам с last-touch
   атрибуцией; сделки лидов без источника не относятся ни к какому
   каналу — это осознанная честность, а «дыра» закроется по мере перехода
   трафика на новые `lst_`-ссылки.
7. **Ширина 375/390 px** — сетка мобильная (480px колонка), проверялась
   визуально на этапе 5; новых широких блоков не добавлено.
