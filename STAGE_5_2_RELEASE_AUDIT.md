## 3. Обнаруженные дефекты

### D1 — КРИТИЧЕСКИЙ (безопасность + функциональность): пустое JSON-тело → 400 на POST-маршрутах

**Факт.** Веб-клиент (`apps/web/src/api/client.ts`) посылал заголовок
`Content-Type: application/json` на КАЖДЫЙ запрос — включая POST-запросы без
тела: `logout`, `refresh`, `pay/deliver/close/cancel/awaiting-payment`
сделок, `suggest-channels`. Fastify 5 по умолчанию отвечает
`400 FST_ERR_CTP_EMPTY_JSON_BODY` на пустое тело с JSON-типом.

**Воспроизведено фактически** (curl против Fastify 5.12.8 — тот же движок,
что у apps/server):

```
POST /api/auth/logout  Content-Type: application/json  (пустое тело)
→ 400 {"code":"FST_ERR_CTP_EMPTY_JSON_BODY"}
→ GET /api/auth/session тем же cookie → authenticated: true  ← СЕССИЯ ЖИВА
```

**Последствия.**
1. «Выйти» на экране «Ещё» НЕ уничтожал серверную сессию: UI уходил на
   /login, но cookie продолжала действовать (TTL по умолчанию 14 дней) —
   приватные данные (сделки, лиды, поставщики, реквизиты с р/с) оставались
   доступны без повторного ввода пароля. Прямое нарушение требования
   «logout очищает приватное состояние».
2. Действия сделок «оплатить/отгрузить/доставить/закрыть/отменить» и подбор
   каналов падали с 400 — рабочий процесс сделки из браузера был сломан.

**Почему тесты 5.1 не ловили.** Тесты вызывают маршруты через
`app.inject({...})` БЕЗ content-type — парсер тела не включается, дефект
не проявлялся. Реальный браузер посылает заголовок всегда. Найдено именно
браузерным аудитом (п. 11).

## 6. Аудит всех API-маршрутов

Глобальный guard (`apps/server/src/auth/guard.ts`): onRequest-хук на ВСЁ
`/api`; allowlist публичных путей; приватное = действующая сессия, 401 для
всех методов. Проверено по коду каждого роут-файла + тест
«GET приватного без сессии → 401».

**Публичные (6) и причина:**

| Маршрут | Метод | Почему публичный |
|---|---|---|
| /api/health | GET | живость для Render health-check; данных не раскрывает |

**Приватные (guard) — полный перечень модулей и методов:**

readiness), POST /api/auth/refresh.

Отдельно проверенные требования:
- отсутствующие OWNER_LOGIN/OWNER_PASSWORD_HASH: вход 503
  AUTH_NOT_CONFIGURED, приватные маршруты закрыты — тест
  «fail-closed» проходит; приложение не открывается без входа;
- истёкшая сессия: `find()` удаляет истёкшую запись, guard → 401 → браузер
  уходит на /login (браузерная проверка на 2 разрешениях);
- повторное использование cookie после logout: серверная запись удалена —
  401 (тест + браузер); **до исправления D1 logout не работал** (см. D1);
- рестарт сервера: сессии в БД (OwnerSession) — переживают рестарт; токен
  только SHA-256-хеш в БД, cookie HttpOnly;
- просроченные сессии: удаление при обращении + лениво на каждом входе
  (`deleteExpired`); заметка: без входа владельца старые истёкшие записи
  копятся (не работают — не риск);
- подделка Origin: Origin задаётся браузером; неавторизованный Origin на
  изменяющих запросах → 403; отсутствие Origin (сервер-сервер) не
  обходит авторизацию — cookie всё равно нужна;
- rate limit входа: скользящее окно в памяти, 10 неудач / 15 мин → 429
  (тест проходит); IP из X-Forwarded-For за прокси Render;
- cookie за reverse proxy: Secure при NODE_ENV=production, SameSite=Lax,
  Path=/, Max-Age=TTL; обход для локального http — AUTH_INSECURE_COOKIE=1;
- /login без циклов: клиент редиректит только с не-/login страниц,
  auth-запросы исключены; после 401 — один redirect с возвратом
  (?redirect=…); LoginScreen при живой сессии уходит внутрь — петель нет
  (браузерные проверки «нет циклических переходов» на 375/390).

## 7. CSRF / CORS / браузерная безопасность

- Origin-глубина (поверх SameSite): все POST/PATCH/PUT/DELETE на /api
  (кроме webhook со своим секретом) с посторонним Origin → 403
  FORBIDDEN_ORIGIN — тест «POST с посторонним Origin → 403» проходит.
  Поведение по случаям: доверенный Origin — пропуск; посторонний — 403;
  без Origin — пропуск до авторизации (сервер-сервер с украденной cookie
  всё равно 401 без сессии — Origin не фактор аутентичности для
  не-браузера); неправильный Sec-Fetch-Site — не проверяется отдельно,
  т.к. Origin+SameSite=Lax закрывают браузерные векторы (замечание, не
  дефект: CSRF-токен не потребовался — приложение с единственным
  владельцем, все изменяющие запросы покрыты Origin-проверкой + Lax);
- cookie с действительной сессией, но недоверенным источником: POST → 403
  (Origin проверяется до хендлера), GET-чтение из чужого origin — CORS не
  даёт читать ответы (нет ACAO для чужих), сама cookie SameSite=Lax не
  уйдёт на межсайтовый GET-запрос fetch;
- CORS: wildcard **отсутствует** (origin-callback точным совпадением из
  TRUSTED_ORIGINS, дефолт — домен веб-приложения + localhost-порты);
  credentials только для доверенных; подмена доверенного Origin невозможна
  (точное сравнение scheme+host+port, нормализация регистра/слэшей);
  preflight OPTIONS пропускается guard-ом и обрабатывается CORS-плагином —
  «не зависает» (браузерные тесты на реальных запросах);
  CORS нельзя обойти «альтернативным маршрутом» — guard глобален на /api.

## 9. Telegram и Python-парсер

### Telegram (код + тесты)
- setup-webhook: URL **только из серверной конфигурации**
  (TELEGRAM_WEBHOOK_URL / RENDER_EXTERNAL_URL) — тело запроса
  игнорируется; тест «тело с url игнорируется, маршрут закрыт
  авторизацией» проходит; перенаправить апдейты бота на произвольный URL

- публикация: требует сессию владельца (guard) + бот-админ канала

  `confirm: true` обходит ТОЛЬКО анти-бан «1 публикация/24 ч» — это
  задокументированное ручное подтверждение, бизнес-ограничения
  (админ-права, доступность канала) остаются;
- webhook: секрет обязателен (fail-closed 403 WEBHOOK_NOT_CONFIGURED),
  сравнение timing-safe (`safeEqual`), неверный секрет → 401 без
  деталей внутренностей; ошибки Telegram глушатся (200) чтобы не было
  ретраев; секрет в логи не пишется (в warn — только факт «не задан»);
- секрет по умолчанию детерминирован sha256("agropost:"+token) — стабилен
  между рестартами.

### Python-парсер (код + 39 pytest)
- без PARSER_SECRET `/run` закрыт 503 (fail-closed) — тесты этапа 5.1
  проходят; секрет проверяется на /run; **наблюдение**: GET /status
  и /health сервиса парсера секретом не защищены — на Render это
  отдельный private-сервис по внутренней сети (в render.yaml он
  закомментирован), наружу не публикуется; при раскомментировании блока
  следует оставить сервис приватным (отражено в инструкции п. 12);
- Node передаёт секрет только сервер-сервер (заголовок X-Parser-Secret
  из env, в клиент не попадает, не логируется; /api/parser/* под guard
  владельца);
- MTProto-сбор выключен по умолчанию: `TG_COLLECT_ENABLED=0` (bool из env,
  включается только явной "1/true/yes/on"); даже при явном источнике
  TELEGRAM адаптер отвечает «disabled» — включить «неправильной

## 14. Что осталось непроверенным и почему

1. **2 интеграционных DB-теста парсера** — требуют реальный PostgreSQL;
   в песочнице его нет (глобальный DATABASE_URL указывает на SQLite-файл).
   Не код-дефект: тесты корректно skip-аются без DATABASE_URL.
2. **`prisma migrate deploy` самим Prisma-раннером против реального PG**
   (контрольные суммы `_prisma_migrations`, пересоздание прод-состояния) —
   применялся идентичный SQL в идентичном порядке на PGlite (PostgreSQL 19),
   но прод — Neon (другая мажор-версия). Обязательно к прогону на
   стейджинг-базе: сначала `migrate deploy` на копии, затем на стейджинге.
3. **Живые вызовы Telegram Bot API** (webhook set/getChatMember/publish) —
   тесты используют фейковый Telegram-клиент; реальный токен не
   задействовался (прод-действия запрещены заданием).
4. **Реальный деплой на Render/Neon и «спящий» free-tier** — не выполнялся
   осознанно (без разрешения на прод-деплой).
5. **AI golden-set интеграционные тесты** (`test:golden`) требуют ключей
   внешних провайдеров — не запускались; юнит-тесты, кэш, каскад моделей
   и fallback покрыты в основном прогоне (180).
6. **Rate-limiter и сессии при нескольких инстансах** — архитектура
   single-instance (Render free) — горизонтальное масштабирование не
   заявлено.
